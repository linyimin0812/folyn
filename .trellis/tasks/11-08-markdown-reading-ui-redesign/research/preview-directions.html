缓存失效策略：从定时刷新到事件驱动

2026-11-08notes/architecture/cache.md约 4 分钟

编辑器在打开大型知识库时，需要缓存文件树、全文索引和渲染结果。过去我们用 setInterval 每 30 秒刷新一次，简单可靠，但在多人同步的场景下，旧数据会在界面上停留最长半分钟。这篇笔记记录我们如何改成事件驱动的失效机制，以及踩过的坑。

01问题出在哪里

定时刷新有两个明显代价：一是空闲时也在做无用功，二是刷新粒度太粗。改一个文件，整棵树都要重新读一遍。真正需要的是只让受影响的那一小块缓存失效。

  • 文件树：只需要更新被改动的目录节点
  • 全文索引：按文件增量重建，而不是全量重扫
  • 渲染结果：以文件内容哈希为键，内容不变就直接复用

缓存失效是计算机科学中最难的两件事之一。真正难的不是“什么时候清”，而是“清哪一块”。

02事件驱动的实现

文件系统监听器把变更合并成批次，每个批次只带路径和变更类型。订阅方各自决定要不要失效，互不干扰。详细的事件格式见 同步协议文档。

TYPESCRIPTwatcher.ts
export function onBatch(changes: FileChange[]) {
  // 同一路径在一个批次内只保留最后一次变更
  const latest = new Map(changes.map((c) => [c.path, c]));
  for (const change of latest.values()) {
    treeCache.invalidate(dirname(change.path));
    renderCache.drop(change.path);
  }
}

批次窗口取多大

窗口太小，批量操作（比如 git checkout）会触发上百次失效；太大又会让界面反应迟钝。实测下来 120ms 是比较平衡的取值。

批次窗口失效次数界面延迟

提示

渲染缓存用内容哈希做键之后，撤销再重做同一段修改也能直接命中缓存。
