# AI Chat Provider Catalog & Model Registry

## Problem Statement

As a Quill user, when I open **Settings → AI → Chat 模式** to configure my LLM provider, I see only three entries in the provider dropdown — Anthropic, OpenAI, and "OpenAI 兼容". This is too narrow for the ecosystem: rig 0.40 supports 18 providers (Anthropic, OpenAI, Azure OpenAI, Cohere, DeepSeek, EternalAI, Google Gemini, Galadriel, Groq, HuggingFace, Hyperbolic, Mira, Moonshot, Ollama, OpenRouter, Perplexity, TogetherAI, xAI), most of which I would use if they were a one-click option instead of a manual `base_url` lookup. For every provider I also have to manually type the model id (e.g. `claude-sonnet-4-6`, `deepseek-chat`) — I either keep a browser tab open to the provider's docs or guess, and either way the id can be wrong or stale. And I have no idea whether the model I picked supports image input until I try uploading an image and watch the chat fail.

The downstream consequence is that the Bubble Template AI Agent, Pet Chat, and any other consumer of `runRigChat` are constrained to a hand-typed Anthropic / OpenAI / custom-endpoint triangle, when rig's value proposition is exactly that switching providers should be a one-line change.

## Solution

Extend the Chat 模式 settings section with **a 20-entry provider catalog** (18 rig-supported providers + OpenAI 兼容 + Anthropic 兼容), **per-provider configuration forms** that render only the fields each provider needs (Azure gets `deployment_id` + `api_version`, Ollama hides `api_key`, everyone else gets the standard `api_key` + `model` + `base_url` triplet), and **an inline "获取 API key →" link** next to the api_key label for each provider's signup page.

Replace the free-text **Model** input with a **fetched model dropdown**: a per-provider "获取模型" button calls a new Rust Tauri command `list_models(provider_id, api_key, base_url, ...)`, which routes to the appropriate fetcher — rig's native `ModelListingClient::list_models()` for the 7 providers that implement it (anthropic, openai, gemini, deepseek, ollama, openrouter, mira), a raw HTTP `/v1/models` + Bearer fallback for the 11 OpenAI-compatible family providers, and a dedicated raw HTTP strategy for Azure (different auth header + query parameter). Fetched model id lists are persisted to a single aggregated JSON file `~/.quill/models.json`, keyed by provider id.

A second "重新拉取全部" button in the section header iterates every configured provider (those with `api_key` non-empty) and refreshes their section of the JSON file in parallel.

Each fetched model is enriched at read time with **capability metadata** (modalities, reasoning, pricing, web search, function call) sourced from a build-time catalog JSON shipped with the app. The catalog is generated by a sync script that pulls `https://models.dev/api.json` and OpenRouter's text/image model lists, validates with zod, and writes to `packages/model-registry/data/models-catalog.json` (committed to the repo; refreshed by manually running the script before releases). At runtime, `mergeProviderModelsWithRegistry(remote_ids, catalog)` produces the final `Model` objects that the dropdown renders — each row shows `id · capability badges · pricing`, and `isVisionModel(m)` / `isReasoningModel(m)` / `isWebSearchModel(m)` pure functions drive UI affordances (e.g. disable the image upload button in `BubbleTemplateAIChatModal` when the selected model lacks vision).

The catalog generation script trusts models.dev's aggregation rather than reimplementing Cherry Studio's 18-vendor-file + reasoning-rule-table machinery — models.dev already reports capabilities, reasoning, and pricing per model, so a single fetch + zod validation is sufficient.

The Rust side (`chat.rs`) is extended from 2 match arms (anthropic / openai fallback) to a 20-arm route table that instantiates the correct rig provider client per provider id (or the raw HTTP fetcher for the 11 OpenAI-compat family + Azure). Backwards compatibility: the existing persisted `chatProvider` values `'anthropic'`, `'openai'`, `'openai-compatible'` are kept verbatim — old settings hydrate without migration. Two new persisted fields (`chatAzureDeploymentId`, `chatAzureApiVersion`) are added to `PERSIST_KEYS_AI_CONFIG` but only rendered when `provider === 'azure-openai'`.

## User Stories

1. As a Quill user, when I open Settings → AI → Chat 模式, I want to see a 20-entry provider dropdown grouped into "原生" (Anthropic, OpenAI, Azure OpenAI, Cohere, Gemini, HuggingFace, Ollama), "兼容" (OpenAI 兼容, Anthropic 兼容), "OpenAI 兼容家族" (DeepSeek, EternalAI, Galadriel, Groq, Hyperbolic, Mira, Moonshot, OpenRouter, Perplexity, TogetherAI, xAI), so that I can pick a provider without scrolling through an unstructured 20-item flat list.
2. As a Quill user, when I select "DeepSeek" from the dropdown, I want the `base_url` field to pre-fill with `https://api.deepseek.com` (DeepSeek's default endpoint) so that I don't have to look it up.
3. As a Quill user, when I select "OpenAI" or "Anthropic", I want the `base_url` field to stay empty (the provider's default endpoint is implicit) so that I'm not forced to fill a field I don't need.
4. As a Quill user, when I select "Azure OpenAI", I want two additional fields — `deployment_id` and `api_version` — to appear below the standard three, so that I can supply the parameters Azure uniquely requires.
5. As a Quill user, when I select "Ollama", I want the `api_key` field to be hidden entirely (Ollama runs locally without auth) so that I'm not asked for a credential that doesn't exist.
6. As a Quill user, for every provider that requires an api key, I want a "获取 API key →" link next to the api_key label that opens the provider's signup page (e.g. `https://console.anthropic.com/settings/keys` for Anthropic, `https://platform.openai.com/api-keys` for OpenAI, `https://console.groq.com/keys` for Groq), so that I don't have to google "how do I get an API key for X".
7. As a Quill user, for Ollama (which has no api key), I want no "获取 API key" link rendered so that I'm not offered a link to a page that doesn't exist.
8. As a Quill user, after I fill in api_key (and base_url if needed) for a provider, I want a "获取模型" button next to the model field that fetches the provider's available model list, so that I can pick a model from a dropdown instead of typing an id I memorized.
9. As a Quill user, when I click "获取模型", I want the button to show a loading spinner and the model field to convert to a dropdown once results arrive, so that I have visual feedback that the fetch is in progress.

11. As a Quill user, when the fetch fails (wrong api_key, network error, provider 5xx), I want a clear inline error message and the model field to remain as a free-text input, so that I can either fix the api_key or type a model id manually as a fallback.
12. As a Quill user, when I select a model from the dropdown, I want my choice persisted across app restarts, so that I don't have to re-pick on every launch.
13. As a Quill user, when I previously selected a model that is no longer in the freshly-fetched list (provider deprecated it), I want the dropdown to still show the old id with a "已不在可用列表" greyed-out marker, so that my setting isn't silently lost and I'm prompted to pick a replacement.
14. As a Quill user, I want a "重新拉取全部" button in the Chat 模式 section header that re-fetches model lists for every provider I have configured (those with api_key non-empty), so that I can refresh all my catalogs at once when providers ship new models.

17. As a Quill user, when I open Settings → AI → Chat 模式 after a previous fetch (cached in `~/.quill/models.json`), I want the model dropdown for my selected provider to be pre-populated from the cache without requiring a fresh fetch, so that the UI is responsive on first paint.
18. As a Quill user, when I pick a model that supports image input (vision capability) and I'm in `BubbleTemplateAIChatModal`, I want the image upload button to be enabled, so that I can attach a design reference image.
19. As a Quill user, when I pick a model that does NOT support image input and I'm in `BubbleTemplateAIChatModal`, I want the image upload button to be disabled with a tooltip "当前模型不支持图片输入", so that I don't waste a turn uploading an image the model will reject.
20. As a Quill user, when I pick a reasoning-capable model (e.g. Claude with extended thinking, OpenAI o-series), I want a "thinking budget" input exposed in the Chat 模式 section, so that I can control how much reasoning the model does.
21. As a Quill user, when I pick a non-reasoning model, I want the "thinking budget" field hidden, so that I'm not offered a control that does nothing.
22. As a Quill user, when I previously configured `chatProvider: 'openai-compatible'` with a custom `chatBaseUrl` and a `chatModel` (before this update), I want my settings to keep working after the update without any migration step, so that the upgrade is invisible.
23. As a Quill user, when I previously configured `chatProvider: 'anthropic'` or `'openai'`, I want those to keep working identically, so that the upgrade is invisible.
24. As a Quill user, I want the provider display names localized (e.g. "OpenAI 兼容" in zh, "OpenAI Compatible" in en) so that the UI matches my locale.
25. As a Quill user, I want provider brand names (DeepSeek, Groq, OpenRouter, Anthropic, OpenAI, etc.) to remain in their original form across locales, so that I recognize them regardless of language.
26. As a Quill user, when I click "测试连接" (existing button), I want the test to use my currently-selected provider's native rig client (not the openai fallback) so that the test reflects the actual chat path.
27. As a Quill user configuring Azure OpenAI, I want the test button to use my `deployment_id` and `api_version` so that the test reflects the actual Azure request shape.
28. As a Quill user configuring Ollama, I want the test button to work even though I haven't filled an api_key, so that local Ollama instances are testable.

30. As a Quill user, when I switch providers after filling in fields for one provider, I want the per-provider fields (e.g. Azure's `deployment_id`) to be preserved when I switch away and back, so that I don't lose my Azure config by experimenting with another provider.
31. As a Quill user, when I look at the model dropdown, I want vision-capable models to show a small "vision" badge, reasoning models to show "reasoning", web-search-capable models to show "web", so that I can scan capabilities visually.
32. As a Quill user, when I look at the model dropdown, I want pricing shown as a subtitle (e.g. "$3 / $15 per Mtok") so that I can compare cost across models.
33. As a developer integrating a new provider into Quill later, I want the provider catalog in `apps/desktop/src/services/providers/catalog.ts` to be the single source of truth for the provider's display name, default base_url, default model placeholder, api key signup URL, category, and field visibility, so that adding a provider is one file edit.
34. As a developer, I want the Rust side to route by provider id via a 20-arm `match` in `chat.rs` and `list_models.rs`, so that the routing logic is co-located and auditable.
35. As a developer, I want the catalog generation script (`scripts/sync-model-catalog.ts`) to be runnable manually before releases, so that the catalog JSON stays fresh without a CI dependency.
36. As a developer, I want the catalog JSON to be zod-validated at runtime when first loaded, so that a malformed catalog (e.g. models.dev changes their schema) fails loudly instead of producing broken UI.
37. As a developer, I want the `~/.quill/models.json` cache file to be keyed by provider id at the top level, so that refreshing one provider's list doesn't require reading+writing the whole file under a lock.

## Implementation Decisions

### Provider catalog (frontend, single source)

A new TypeScript module `apps/desktop/src/services/providers/catalog.ts` declares the 20 providers. Per-provider fields:

- `id` — canonical string key (`'anthropic'`, `'openai'`, `'azure-openai'`, `'cohere'`, `'deepseek'`, `'eternalai'`, `'gemini'`, `'galadriel'`, `'groq'`, `'huggingface'`, `'hyperbolic'`, `'mira'`, `'moonshot'`, `'ollama'`, `'openrouter'`, `'perplexity'`, `'together'`, `'xai'`, `'openai-compatible'`, `'anthropic-compatible'`)
- `category` — `'native' | 'compat' | 'openai-family' | 'local'`
- `i18nKey` — `settings:ai.chat.provider.<id>`
- `defaultBaseUrl` — string or `null` (null = no default, user must fill)
- `placeholderModel` — string placeholder for the model field (e.g. `'claude-sonnet-4-6'`, `'deepseek-chat'`)
- `apiKeyUrl` — string URL or `null` (null = no signup link rendered, e.g. Ollama)
- `requiresApiKey` — boolean (false for Ollama)
- `requiresAzureFields` — boolean (true only for `'azure-openai'`)
- `rigClientKind` — `'anthropic' | 'openai' | 'azure' | 'cohere' | 'gemini' | 'huggingface' | 'ollama' | 'openai-compat'` (used by Rust routing, but the source of truth lives here; Rust mirrors via a 20-arm `match`)

The `ChatProvider` type in `aiConfigStore.ts` is widened from `'anthropic' | 'openai' | 'openai-compatible'` to a union of all 20 ids. The `isChatProvider` type guard accepts all 20. **Backwards compatibility:** the three existing ids are kept verbatim; no migration logic in `hydrate`.

### Store layer (`aiConfigStore.ts`)

Add two new persisted keys: `chatAzureDeploymentId`, `chatAzureApiVersion`. Extend `AiConfigState` interface with these + setters. The existing `chatProvider` / `chatModel` / `chatApiKey` / `chatBaseUrl` keys are unchanged — they hydrate as before for the 3 old ids. Setters follow the existing `schedulePersist()` pattern.

A new sibling store `modelRegistryStore` (or a slice inside `aiConfigStore` — implementer's choice based on existing convention) holds the in-memory model list cache: `modelsByProvider: Record<providerId, Model[]>`, `fetchStatus: Record<providerId, 'idle' | 'loading' | 'success' | 'error'>`, `fetchError: Record<providerId, string>`. This store is hydrated from `~/.quill/models.json` on app boot and writes back to the file on every successful fetch.

### Model object shape (runtime)

```ts
type Model = {
  id: string;
  providerId: string;
  capabilities: Capability[]; // ['vision', 'reasoning', 'web-search', 'function-call', ...]
  inputModalities: string[]; // ['text', 'image', ...]
  pricing?: { inputPerMtok?: number; outputPerMtok?: number };
};
```

### Capability pure functions (`apps/desktop/src/services/modelRegistry/capabilities.ts`)

§8 subset, all pure:

- `isVisionModel(m)` — `m.capabilities.includes('vision') || m.inputModalities.includes('image')`
- `isReasoningModel(m)` — `m.capabilities.includes('reasoning')`
- `isWebSearchModel(m)` — `m.capabilities.includes('web-search')`
- `isFunctionCallingModel(m)` — `m.capabilities.includes('function-call')`

### Merge function (`apps/desktop/src/services/modelRegistry/merge.ts`)

`mergeProviderModelsWithRegistry(remoteIds: string[], catalog: Catalog, providerId: string): Model[]`:

- For each id in `remoteIds`, look up the catalog entry; if found, merge catalog capabilities + pricing; if not found, synthesize a minimal `Model` with `capabilities: []` and no pricing (the catalog simply doesn't know about it — typical for newly-released models).
- For catalog entries whose id is NOT in `remoteIds`, omit them from the merged list (the user's provider doesn't actually serve that model — possibly a different account tier or region).

### SettingsPage Chat 模式 UI (`SettingsPage.tsx`)

The existing Chat 模式 section is refactored:

- Provider `<select>` uses `<optgroup label={t('settings:ai.chat.category.native')}>` etc. per category. Options come from `catalog.ts` (not hardcoded).
- The api_key label row renders the "获取 API key →" link inline on the right when `catalog[provider].apiKeyUrl` is non-null.
- The api_key input is hidden entirely when `!catalog[provider].requiresApiKey`.
- The Azure-specific `deployment_id` and `api_version` inputs render conditionally when `provider === 'azure-openai'`.
- The model field converts from `<input>` to a composite component: a "获取模型" button + a `<select>` (when models are loaded) or `<input>` (when not loaded, as fallback). Each option label is `${id} · ${badges} · ${pricing}`.
- A "重新拉取全部" button is added to the section header (next to the title).
- The "thinking budget" input is rendered conditionally when the selected model `isReasoningModel(m)`.
- The "测试连接" button is reused; its call to `testChatConnection` now passes all relevant fields including Azure extras and uses the Rust route by provider id (not the openai fallback).

### Rust side (`chat.rs` extensions + new `list_models.rs`)

`chat.rs` is extended from 2 match arms to a 20-arm `match params.provider.as_str()`. The arms are grouped:

- `anthropic` + `anthropic-compatible` → existing `anthropic::Client::builder()` arm (already in place).
- `openai` + `openai-compatible` + 11 OpenAI-compat family (deepseek, eternalai, galadriel, groq, hyperbolic, mira, moonshot, openrouter, perplexity, together, xai) → existing `openai::Client::builder().base_url(...)` arm. The `base_url` comes from the frontend (either catalog default or user override). The `/v1` auto-append logic in current `chat.rs:230-234` is removed — each provider's catalog `defaultBaseUrl` already includes the correct path.
- `azure-openai` → new arm using `azure::Client::builder()` with `api_key`, `deployment_id`, `api_version`, and `endpoint` (the user-supplied base_url).
- `cohere` → new arm using `cohere::Client::builder()`.
- `gemini` → new arm using `gemini::Client::builder()`.
- `huggingface` → new arm using `huggingface::Client::builder()`.
- `ollama` → new arm using `ollama::Client::builder()` (no api_key required; skip the empty-api-key guard).

The duplicated `drain_loop` is refactored to a trait-object box (`Pin<Box<dyn Stream<Item = Result<Option<String>, String>> + Send>>`) now that a 3rd+ provider arm exists — the `ponytail:` comment in current `chat.rs:195-201` explicitly names this as the upgrade trigger, and 5 new native arms crosses that threshold.

A new file `apps/desktop/src-tauri/src/list_models.rs` adds the `list_models` Tauri command:

```rust
#[tauri::command]
pub async fn list_models(
    app: AppHandle,
    params: ListModelsParams,
) -> Result<Vec<ModelDto>, AppError>
```

`ListModelsParams` mirrors `ChatParams`'s provider routing fields (`provider`, `api_key`, `base_url`, `azure_deployment_id`, `azure_api_version`).

The command routes via a pure function `fn fetcher_kind(provider_id: &str) -> FetcherKind` (returns `Rig(Kind)` / `OpenAICompat` / `Azure`) which is unit-tested independently of HTTP.

For the `Rig` arm, rig 0.40's `ModelListingClient::list_models()` trait is invoked on the constructed client. For the `OpenAICompat` arm, a raw `reqwest` GET to `<base_url>/v1/models` with `Authorization: Bearer <api_key>` returns `{data: [{id: ...}]}`. For the `Azure` arm, a raw `reqwest` GET to `<endpoint>/openai/models?api-version=<api_version>` with `api-key: <api_key>` header returns `{data: [{id: ...}]}`.

Both commands (`chat_stream`, `list_models`) are registered in `apps/desktop/src-tauri/src/lib.rs:676` alongside the existing `chat::chat_stream`.

### Catalog generation script (`scripts/sync-model-catalog.ts`)

A standalone Node script (run manually before releases):

1. `fetch('https://models.dev/api.json')` → zod-validate → extract per-model `{id, providerId, capabilities, inputModalities, pricing}`.
2. `fetch('https://openrouter.ai/api/v1/models')` + `fetch('https://openrouter.ai/api/v1/embeddings/models')` (the latter to mark `EMBEDDING` capability for entries models.dev might miss).
3. Merge: union by `(providerId, id)`. OpenRouter supplements (e.g. adds pricing for providers models.dev doesn't track); models.dev wins on capabilities (more authoritative).
4. Write to `packages/model-registry/data/models-catalog.json` (committed to repo).

The script does NOT generate 18 vendor files, reasoning rule tables, or `reasoning-families.gen.ts` — models.dev already reports these. The script's zod schema IS its test: a malformed catalog fails the script.

### Runtime catalog loading

A new `packages/model-registry/` package (or folder inside `apps/desktop/src/services/modelRegistry/` — implementer's choice based on whether other consumers exist; current scope is only the desktop app, so a folder is sufficient). The catalog JSON is loaded read-only at app boot via `readFileSync` + zod validation, indexed by `(providerId, modelId)` for O(1) lookup. Idle expiry / re-fetch is NOT needed (the catalog is shipped with the binary; it only changes on app update).

### i18n

Each provider gets an i18n key `settings:ai.chat.provider.<id>` in `apps/desktop/src/i18n/locales/{en,zh}/settings.json`. Capability names get keys `settings:ai.chat.capability.vision` / `.reasoning` / `.web-search` / `.function-call` / `.embedding`. Category labels get `settings:ai.chat.category.native` / `.compat` / `.openai-family` / `.local`. Brand names (DeepSeek, Groq, etc.) are untranslated.

### Orphan model handling

When the persisted `chatModel` is not in the freshly-fetched list for the current provider, the dropdown renders the orphan id at the top with a `已不在可用列表` greyed marker. The Rust `chat_stream` does NOT validate `chatModel` against the cache — it forwards the model id to the provider, which either accepts it (provider still serves a deprecated id) or returns an error that the frontend surfaces normally.

### `/v1` auto-append cleanup

The current `chat.rs:230-234` block that forces base URLs to end in `/v1` is removed. Each provider's catalog `defaultBaseUrl` includes the correct path (`https://api.deepseek.com` for DeepSeek, `https://api.groq.com/openai/v1` for Groq, etc.). User-supplied `base_url` overrides are used as-is.

## Testing Decisions

### Seam 1 — TS store + pure functions (extended)

**Location:** `apps/desktop/src/store/aiConfigStore.test.ts` (extended) + new `apps/desktop/src/services/modelRegistry/merge.test.ts` + `apps/desktop/src/services/modelRegistry/capabilities.test.ts`.

**Prior art:** `aiConfigStore.test.ts` already tests hydration + persist keys for the existing 3-provider enum. Extend with:

- Hydration of `chatAzureDeploymentId` / `chatAzureApiVersion`.
- Hydration accepts all 20 provider ids (parameterized test).
- Hydration of an old `'openai-compatible'` blob (regression — must still produce `chatProvider: 'openai-compatible'`).
- Persist keys set contains the 2 new Azure fields.
- `modelRegistryStore` hydration from a sample `models.json` blob.
- `modelRegistryStore` write-through on fetch success.

**Pure functions (new tests):**

- `mergeProviderModelsWithRegistry`: (a) all remote ids in catalog → enriched; (b) some remote ids NOT in catalog → minimal Model with empty capabilities; (c) catalog entries NOT in remote ids → omitted; (d) empty remote list → empty result.
- `isVisionModel` / `isReasoningModel` / `isWebSearchModel`: table-driven over capability combinations and modality combinations.
- `applyCapabilityOverride` (if the override path is implemented — see Out of Scope): force/add/remove semantics over a base capability list.

**Tauri invoke mock pattern:** the new `list_models` Tauri command is invoked from the frontend via `invoke('list_models', ...)`. Tests mock this with the same pattern as `commandRegistry.test.ts` — return canned `Model[]` for given provider ids, simulate errors, etc.

**Why this seam:** the store is the natural consumer of all routing decisions; pure functions are side-effect-free and trivial to test exhaustively; the Tauri invoke mock pattern already exists. No HTTP, no Rust, no Tauri runtime needed.

### Seam 2 — Rust routing + fetcher (new)

**Location:** `apps/desktop/src-tauri/src/list_models.rs` with `#[cfg(test)] mod tests`.

**Prior art:** `chat.rs` has `#[cfg(test)]` modules with `mockito`-style HTTP mocking already used for the openai-compat path.

**Routing pure function:** `fn fetcher_kind(provider_id: &str) -> FetcherKind` — table-driven test over all 20 ids. No HTTP, no IO. Asserts:

- `'anthropic'` → `Rig(Anthropic)`
- `'openai'` → `Rig(OpenAI)`
- `'openai-compatible'` → `OpenAICompat`
- `'deepseek'`, `'groq'`, `'hyperbolic'`, `'mira'`, `'moonshot'`, `'openrouter'`, `'perplexity'`, `'together'`, `'xai'`, `'galadriel'`, `'eternalai'` → `OpenAICompat`
- `'azure-openai'` → `Azure`
- `'cohere'`, `'gemini'`, `'huggingface'`, `'ollama'` → `Rig(Cohere)` / `Rig(Gemini)` / `Rig(HuggingFace)` / `Rig(Ollama)`
- Unknown id → `Err` (or `OpenAICompat` fallback — decision for implementer).

**HTTP-level tests with `mockito`:**

- Anthropic: mock server returns `{data: [{id: "claude-sonnet-4-6"}, ...]}`, asserts the request had `x-api-key` header + `anthropic-version: 2023-06-01` header.
- OpenAI-compat (DeepSeek): mock server at `https://mock.test/v1/models` returns `{data: [{id: "deepseek-chat"}]}`, asserts `Authorization: Bearer <key>` header.
- Azure: mock server at `https://mock.test/openai/models?api-version=2024-10-21` returns `{data: [{id: "gpt-4o"}]}`, asserts `api-key: <key>` header.
- Ollama: mock server at `https://mock.test/api/tags` returns `{models: [{name: "llama3.2"}]}`.
- Error paths: 401, 5xx, network failure → `AppError` with a meaningful message.

**JSON file round-trip:** `tempdir` + write `~/.quill/models.json` sample + read back + assert enriched `Model[]`.

**Why this seam:** the store mock in Seam 1 cannot verify that the Rust side actually sends the right auth header to the right endpoint — only Rust-side tests can. The routing pure function is the cheapest correctness check; the `mockito` tests catch auth-header mistakes that would otherwise surface as user-visible "401 Unauthorized" errors in production.

### What is NOT tested

- The `SettingsPage` Chat 模式 component render — by design. The store seam covers all state transitions; the component is a thin render of store state. Conditional render of Azure fields is a 1-line `provider === 'azure-openai' &&` check, not worth a component test.
- The catalog sync script — by design. The runtime zod schema is the test. If models.dev ships a schema change, the sync script fails loudly; runtime loading of the shipped JSON re-validates with the same schema.
- Visual appearance of capability badges / pricing subtitle — by design. Visual regression is a designer review, not an automated test.

## Out of Scope

- **§5 reasoning rule table + custom-id heuristics.** Models.dev reports reasoning per model; Quill does not need to infer reasoning from id patterns. Cherry Studio's `reasoning-families.gen.ts` machinery is not reproduced.
- **§6 user overrides of model capabilities.** Users cannot edit the capabilities of a model in the UI (no "force vision on / off" toggle). The `~/.quill/model-overrides.json` concept from the doc is not implemented. `applyCapabilityOverride` may be implemented as a pure function (with a no-op override input) for forward-compatibility, but no UI surfaces it.
- **§7 SQLite.** The doc's `user_model` table with `userOverrides` tracking is not built. JSON file persistence (`~/.quill/models.json`) is sufficient for Quill's read pattern.
- **Image generation, audio, embedding, rerank models.** Only chat / completion models are surfaced in the dropdown. Models.dev returns all modalities; the merge function filters to chat-relevant modalities (text output, optionally image input).
- **Per-provider model search / filter UI.** The dropdown is a flat list per provider. No fuzzy search, no capability filter checkboxes. The 20-100 models per provider is small enough to scroll.
- **Streaming model list.** The `list_models` command returns a single batch; no SSE / streaming for the model list itself.
- **Provider-specific extras beyond Azure.** Cohere's `client_name`, Gemini's `api_version`, HuggingFace's repo-id-vs-model-name distinction — all are either auto-handled by rig's native client or accept the user's single `model` field input. No per-provider UI fields are added for these.
- **CI integration of the catalog sync script.** The script is run manually before releases; no GitHub Action, no pre-commit hook. A maintainer runs `node scripts/sync-model-catalog.ts` when refreshing the catalog.
- **Galadriel and EternalAI native rig clients.** These two providers are listed in rig's docs but are not in rig 0.40's `src/providers/` directory. They route through the `OpenAICompat` raw HTTP fallback. If a future rig version exposes them natively, the routing pure function is updated in one place.
- **Migration of old `'openai-compatible'` settings.** The id is kept verbatim; no migration logic.
- **Capability badges for OpenAI-compat escape hatch (`'openai-compatible'`, `'anthropic-compatible'`).** These providers have no catalog entries (the user's custom endpoint isn't in models.dev). The merge function returns minimal `Model` objects with `capabilities: []`. The dropdown shows ids without badges.

## Further Notes

### Why all 18 providers natively in one PR (vs. phased)

The user explicitly chose all-at-once over a phased rollout. The cost is 5 new native rig client arms in `chat.rs` (Azure, Cohere, Gemini, HuggingFace, Ollama), each requiring a real API key to manually verify. The benefit is a single coherent provider catalog UI with no "coming soon" markers. The trade-off is documented in the grilling session and accepted.

### Why a single aggregated `~/.quill/models.json` (vs. per-provider files)

The user chose a single aggregated file over per-provider files despite the slightly worse atomicity (one provider's fetch failure could leave the file half-written). The implementer should write the file atomically: write to `~/.quill/models.json.tmp` then `rename` to `~/.quill/models.json` only after all per-provider fetches in "重新拉取全部" have settled. Per-provider "获取模型" writes the whole file after reading the current state, merging the single provider's section, and writing back.

### Why models.dev as the catalog source (vs. self-built 18 vendor files)

Models.dev aggregates provider model metadata (capabilities, modalities, reasoning, pricing) from a single source. Reimplementing Cherry Studio's 18-vendor + reasoning-rule-table machinery would duplicate that aggregation work with no incremental value. The catalog sync script is ~50 lines of fetch + zod + write; the equivalent machinery in Cherry Studio is ~1500 lines. The trade-off is dependency on models.dev's schema stability — mitigated by the runtime zod validation that fails loudly on schema drift.

### Why a single i18n key per provider (vs. raw strings)

The user explicitly chose full i18n keys for all 20 providers + capabilities + categories, accepting the 20×2 = 40 placeholder entries where the brand name is untranslated. This is consistent with the existing 3-provider pattern and lets future locales (e.g. ja, ko) translate capability names without code changes.

### Adjacent ADRs / context

- **ADR-0001** (referenced in `CONTEXT.md`) — established that the Bubble Template AI Agent is a multi-turn chat (not an agent loop), backed by `runRigChat`. This task extends the chat-mode backend that ADR-0001 depends on; it does not change the agent-vs-chat decision.
- **`CONTEXT.md`** — defines "Bubble Template AI Agent" and "Feature Agent" vocabulary. The Bubble Template AI Agent is a downstream consumer of this work (its image upload affordance becomes model-aware); the Feature Agent path is untouched (still uses `claude-cli` sidecar).

### Test seam decision rationale

Two seams (TS store + pure functions; Rust routing + fetcher) is the minimum. The skill's "ideal number is one" is unreachable here because TS and Rust are different language runtimes — a store-level mock cannot verify that the Rust side sends `x-api-key` (not `Bearer`) to Anthropic. The Rust seam is small (one file, one routing function, four `mockito` tests) and the TS seam extends an existing test file, so the marginal cost is low.
