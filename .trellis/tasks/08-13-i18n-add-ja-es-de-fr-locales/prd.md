# i18n: add ja/es/de/fr locales

## Goal

Add Japanese (ja), Spanish (es), German (de), French (fr) translations alongside existing zh/en, so the app ships with 6 locales. User picks locale in Language Switcher; runtime switches via existing Zustand store + i18next.

## Requirements

- Add `ja, es, de, fr` to `SUPPORTED_LOCALES` in `apps/desktop/src/i18n/index.ts`; widen `Locale` type union.
- Widen `detectInitialLocale()` to recognize `ja`, `es`, `de`, `fr` navigator prefixes; otherwise unchanged (still falls back to `zh`).
- Add 4 × 16 = 64 new JSON files at `apps/desktop/src/i18n/locales/{ja,es,de,fr}/{namespace}.json`, each with the same key tree as the corresponding `en/*.json`. Translations generated by me (the assistant) during implementation.
- Extend `LanguageSwitcher.tsx` `LOCALE_LABELS` to 6 entries: `{ zh: '中文', en: 'English', ja: '日本語', es: 'Español', de: 'Deutsch', fr: 'Français' }`.
- Update each locale's `common.json` to add `language.ja/es/de/fr` keys for parity (even though `LanguageSwitcher.tsx` doesn't read them — other consumers may).
- **Rust side unchanged**: `pet_common.rs::pet_menu_label` / `app_menu_label` keep `_ => English` fallback. New locales see English pet/app menu labels. (Documented trade-off — out of scope.)

## Acceptance Criteria

- [ ] All 16 namespaces have JSON files for each of ja/es/de/fr with key trees matching `en` exactly (diff structurally, no missing/extra keys).
- [ ] Switching to ja/es/de/fr in Language Switcher changes UI text with no `i18n missing key` console warnings on common screens (topbar, sidebar, settings, editor, etc.).
- [ ] `detectInitialLocale()` returns `ja`/`es`/`de`/`fr` when `navigator.language` starts with the corresponding prefix; falls back to `zh` otherwise.
- [ ] `LOCALE_LABELS` shows 6 entries; switcher renders all 6 with correct native names.
- [ ] Existing zh/en behavior unchanged (no key removed, no fallback path regressed).
- [ ] `pnpm lint` / typecheck green (no full project build — per user preference).

## Definition of Done

- Lint / typecheck green
- Manual smoke (user does this): launch app, switch through 6 locales, no broken layout / missing keys
- Commit on worktree branch `worktree-i18n-ja-es-de-fr`

## Technical Approach

1. **Wiring first** (small, safe): extend `index.ts` constants + `detectInitialLocale()`, extend `LanguageSwitcher.tsx` `LOCALE_LABELS`. Add stub JSON files (copy of `en/*.json`) so the app builds and switcher works with English-as-fallback for the new locales.
2. **Translations in batches**: translate namespace by namespace, in order: smallest first (`rustErrors`, `terminal`, `search`, `browser`, `vault`, `common`, `topbar`, `shell`, `pet`, `mmap`, `ai`, `study`, `editor`, `sidebar`, `schedule`, `settings`). For each namespace, write all 4 locales before moving to the next namespace.
3. **Parity check**: after each namespace batch, structurally diff key trees against `en/<ns>.json` to catch missing keys.
4. **Final verification**: typecheck, walk through the 4 locales mentally for topbar/sidebar/settings.

## Decision (ADR-lite)

**Context**: App currently ships zh/en only; user wants ja/es/de/fr to broaden reach. 16 namespaces × 4 locales = 64 JSON files (~7500 lines of translations). Two secondary touch points surfaced: Rust menu labels (`pet_common.rs`) and the `LanguageSwitcher.tsx` label map.

**Decision**:
- Translations: I (assistant) generate during implementation, user reviews later.
- Rust menu labels: leave `_ => English` fallback. Full Rust localization is out of scope (small label set, English is acceptable for v1).
- LanguageSwitcher labels: extend the hardcoded `LOCALE_LABELS` map (not switch to i18n keys) — keeps the switcher working even before any locale resources load.

**Consequences**:
- Faster ship; trade-off is that ja/es/de/fr users see English pet menu + macOS app menu bar labels. Fix later by extending `pet_common.rs` match arms — the function signature already takes `locale: &str`, no API change needed.
- Translation quality is bounded by my language ability; user should review `settings.json` (714 lines, lots of UI-critical strings) before release.
- Bundle size grows ~4 × 1880 lines of JSON. Static imports (current pattern) — lazy loading is out of scope.

## Out of Scope

- Rust menu label translation for new locales (English fallback)
- Lazy loading / code-split locale bundles
- RTL layout support
- Translation memory / external TMS integration
- Pluralization / gender refactoring beyond what current keys already do
- Automated translation regression tests (deferred to user review)
